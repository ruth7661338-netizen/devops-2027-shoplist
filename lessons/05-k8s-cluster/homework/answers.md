| רכיב | איפה הוא רץ (הנהלה / כל node) | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה (Control Plane) | שער הכניסה היחיד לקלאסטר: מקבל כל בקשה, מאמת אותה, ושומר או קורא את המצב מ-etcd. | דלפק ההזמנות בקונדיטוריה: כל הזמנה ושאלה עוברת דרכו, ורק הוא רושם וקורא בספר ההזמנות. |

| scheduler | הנהלה (Control Plane) | בוחר לכל Pod חדש את ה-Node המתאים ביותר להריץ אותו. | מנהל המשמרת: מחליט באיזו עמדה ייאפה כל מגש חדש, לפי המקום הפנוי בתנור. |
| controller manager | הנהלה (Control Plane) | מריץ לולאות בקרה שמשוות את המצב בפועל למצב הרצוי ומתקנות פערים. | האחראי על הוויטרינה: אם צריכות להיות 3 עוגות במדף ונמכרה אחת, הוא מזמין הכנה של חדשה. |
| kubelet | כל node | מוודא שהקונטיינרים של ה-Pods ששובצו ל-Node שלו רצים ותקינים, ומדווח ל-API server. | האופה שבעמדה: מקבל את המגשים ששובצו אליו, דואג שייאפו, בודק אותם ומדווח לדלפק. |
| container runtime | כל node | מוריד images ומריץ בפועל את הקונטיינרים, לפי הוראות ה-kubelet. | התנור והמיקסר: הציוד שאופה בפועל, לפי הוראות האופה. |
| kube-proxy | כל node | מתחזק את כללי הרשת ב-Node, כך שתעבורה שנשלחת ל-Service מגיעה לאחד ה-Pods שמאחוריו. | המוכר שליד המדפים: לקוח מבקש "קרואסון", והוא מביא מאחד המגשים שמוכנים כרגע. |
| coredns | כ-Pods בתוך הקלאסטר (בדרך כלל 2 עותקים, ב-namespace בשם kube-system) | שרת ה-DNS הפנימי: מתרגם שמות של Services לכתובות IP. | לוח התפריט: מחפשים מאפה לפי שם ומוצאים באיזה מדף הוא נמצא. |

2.
כשהקונטינר קורס הקובלט מפעיל אותו מחדש 

הkubelet אמור לדאוג שבכל פעם שיש נפילה להרים את הקוד מחדש אבל אם נמחקו הנתונים אין לו אפשרות להעות מחדש ולן יש את הקונטרולר מנהגר שמפעיל את הקוד מחדש.

3.הקובלת מפסיק לדוח שהוא חי הקונטרולר מנהגר מדוח שהוא לא פעיל

אם המחשב נכבה הקלסטר נופל ואין מי שינהל עד שהמשב עולה בחזרה ואז יעלה הקלסטקר.

הקונטרולר רואה שחסר פוד והולך ומיצר חדש הSCHEDULER משבץ אותו והKUBELET מפעיל אותו.


גם ל-Pod בודד יש הגנה חלקית: אם הקונטיינר קורס, ה-kubelet מפעיל אותו מחדש באותו Node (לפי restartPolicy). אבל אם ה-Pod עצמו נמחק, רק controller יכול להחזיר אותו.
